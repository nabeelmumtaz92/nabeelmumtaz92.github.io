Parallel. An AI that multitasks in parallel.

Designing an AI that works on several tasks at the same time. You write one message with one task per line, and Parallel runs them all at once — each answer streaming into its own block, closing with one quiet line on the time saved. The interface stays deliberately familiar, a plain ChatGPT-style conversation, so the new idea is the parallelism, not the UI. The concept calls for an open-source model on local hardware: no third-party AI brand, no sign-in, no API key field. Designed by a team of one; the prototype is being built in Figma Make.

The problem

AI assistants serialize your work.

Every AI assistant makes you do one thing at a time: one message, one answer, wait, repeat. But real work comes in batches — a product description, social copy, an FAQ, a marketing outline, an email campaign. The workaround today is tabs and windows: copy the prompt five times, babysit five conversations, and stitch the answers together yourself.

Parallel's bet is one line: an AI that multitasks in parallel. The interface looks deliberately familiar — a conversation area and one prompt box pinned to the bottom — so the only new thing to learn is that each line is its own task.

The approach

Each line is a task. They all run at once.

On send, the prompt box drops to the bottom. Your message appears as a bubble with each line shown as its own row, and Parallel's reply lists one block per task. Every block shows a small "Running" label with a spinner — all of them at once. As soon as the model starts writing, each block swaps its label for the answer, streaming in word by word, with a small grey duration appearing when the task finishes. The send button turns into a stop button while anything is running.

When all tasks are done, one muted line closes the reply: "5 tasks done in 7.8 s · 52% faster than one at a time." The summary uses real numbers — one at a time is the sum of durations, parallel is the longest one. Copy and Retry icons appear under each answer on hover. No dashboards, no cards-everywhere, no extra screens.

Minimal on purpose. The first prototype used electric cyan on nearly everything and read as flat; the redesign restricts the accent to the send button, the spinner, and the focus ring. Everything else is greys and text. One screen, one accent color, no emoji — ChatGPT quiet, with parallel powers.

The screens

Five states, one screen.

The whole app is a single screen that moves through five states. The prototype in Figma Make is a working React mock: each line of the sample message becomes a task, tasks run with simulated 2–6 second durations, and the summary line uses real numbers.

Empty

A centered "What do you need done?" with the prompt box in the middle of the screen — ChatGPT's new-chat view. Three small suggestion pills sit underneath it. Placeholder: "Ask Parallel."

Design decisionFamiliarity is the onboarding. If it looks like ChatGPT, nobody has to learn the interface — only the idea that each line runs as its own task.

Sent

The prompt box drops to the bottom. The user's message appears as a right-aligned bubble with each line shown as its own row. Enter sends; Shift+Enter adds a new line — a new task.

Design decisionShift+Enter is the whole interaction model, so the helper text under the box says it plainly: "Each line runs as its own task, all at the same time."

⏳In progress

Running

One block per task, every block showing "Running" with a spinner at the same time. No progress bars — they imply a known total that a model doesn't have. The send button becomes a stop button.

Design decisionShowing all tasks as Running simultaneously is the product promise made visible. It's the one moment the app brags about being parallel.

✨In progress

Done

Answers stream in word by word as the model writes; each finished task gets a small grey duration ("2.4 s"). One muted line closes the reply: "5 tasks done in 7.8 s · 52% faster than one at a time."

Design decisionThe savings line is quiet because trust is at stake — local hardware shares power across tasks, so the mock stays at an honest 40–60% faster, never 80%+.
05
🖥️In progress

Engine states

A small muted pill in the top bar reads "Local · Qwen 2.5 7B" — tapping it opens the installed-models menu. If the engine is offline, one muted line appears above the prompt box: "Parallel's engine isn't running. Start it and try again," with a Retry text button. No modal.

Design decisionSelf-hosted is a feature, so the UI shows the engine honestly: which model is running, and exactly what to do when it isn't — never an API key field for a third-party service.

Design principles

Five rules the screens follow.

🎨 Quiet by defaultCyan appears only on the send button, the spinner, and the focus ring. Text and greys do everything else — hierarchy without decoration.
📝 Text does the workNo stat cards, no comparison charts, no "How it works" section. If a number matters, it lives in one muted sentence.
⚖️ Honest about hardwareA local model sharing its GPU across tasks saves less than a cloud API. The design says 40–60% faster and means it.
🖥️ One screenNo sign-in, no settings, no sidebar in v1. New chat clears the screen; follow-up batches just stack below.
♿ Accessible by constructionText contrast at least 4.5:1, visible focus rings on the prompt box and buttons, touch targets at least 44 × 44 pt.

What's next

From prototype to a local engine.

The concept is an open-source model on local hardware — Ollama on a Mac to start, a GPU server running vLLM later — and the design already accounts for that transition.

  • Engine integration — swap simulated durations for the real local model; the model chip and streaming states are already designed for it Planned
  • iOS native — same single-screen layout with a standard nav bar, plus a light haptic when each task finishes Planned
  • Verified savings — measure real parallel-vs-sequential time on the actual hardware and let the summary line report it Planned

Outcomes & context

A design with the physics built in.

Parallel is a rare design where the UX copy and the engineering are the same document: the summary line's math (one-at-a-time = sum of durations, parallel = longest) is specified in the brief, the streaming states map to how a local model actually emits tokens, and the savings figure is calibrated to shared hardware instead of cloud fantasy.
